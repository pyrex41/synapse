## Domain

- Search Platform
- Machine Learning
- AI/ML Infrastructure

## Maturity (0-5)

**Current score: 2 / 5 (Repeatable)**

- **Level 0 - Initial**: No AI augmentation. Search is purely keyword-based BM25 with static field boosts. No ML models in the search pipeline.
- **Level 1 - Ad hoc**: Experimental vector search has been prototyped in a development environment. No production deployment. Embeddings generated manually by engineers for one-off relevance tests.
- **Level 2 - Repeatable** (current): Hybrid search is deployed to production: BM25 + HNSW vector search merged via Reciprocal Rank Fusion. Document embeddings generated by OpenAI text-embedding-3-small and cached in Redis. LightGBM re-ranking model is trained weekly from click signal data and deployed to the Search Relevance Engine. Query embedding generated inline at search time with a 50ms timeout and graceful fallback to BM25-only.
- **Level 3 - Defined**: Formal model evaluation framework with held-out test set and NDCG@10 regression gate. Model versioning and rollback procedures documented. Embedding API dependency has an SLO and fallback strategy documented. A/B testing framework for model variants is operational.
- **Level 4 - Managed**: Online evaluation via interleaved ranking experiments. Model retraining is fully automated with no manual intervention. Embedding cache hit rate and vector index quality metrics tracked and alerting on degradation.
- **Level 5 - Optimizing**: Continuous online learning loop where click signals retrain the model without a weekly batch cycle. Multi-modal search (image + text). Retrieval-augmented generation (RAG) for direct answer synthesis from indexed content.

**Gap to Level 3**: The immediate gap is a formal model evaluation framework. Currently, LightGBM model promotion is based on manual offline NDCG@10 evaluation by an engineer. This needs to be replaced by an automated regression gate in the deployment pipeline. Additionally, the embedding API fallback behavior is implemented in code but not formally documented as a runbook or SOP.

## Metrics

- Hybrid search coverage: 100% of production search queries (BM25+vector when embedding available)
- Embedding API availability (fallback to BM25-only when unavailable): 99.2% inline embedding success rate
- Redis embedding cache hit rate: 67% (document-level), reducing OpenAI API calls
- LightGBM model NDCG@10 vs. BM25 baseline: +0.09 improvement (0.74 vs. 0.65)
- Re-ranking P95 latency contribution: 18ms (within 20ms budget)
- Embedding batch throughput: up to 32 documents per API call; 7-day TTL on cached vectors

## Notes

This capability is in draft status because the governance framework for AI/ML in production is still being established. The technical implementation (hybrid search, LightGBM re-ranking) is live in production, but the formal policies, evaluation standards, and documentation required to move to "accepted" status are still being developed.

Key blockers for moving to accepted:
- POLICY-023 (AI/ML Model Governance) is in draft and not yet ratified — once ratified, CAPABILITY-015 can reference it as a formal evidence link
- Automated model evaluation gate in the deployment pipeline is not yet implemented (tracked in the engineering backlog)
- Runbook for embedding API degradation (covering both inline query embedding failure and bulk document embedding backlog) is not yet written
