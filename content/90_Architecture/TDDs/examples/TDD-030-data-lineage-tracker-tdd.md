## Summary

Design the Data Lineage Tracker — a service that captures column-level lineage for all data lake tables by parsing dbt manifest artifacts and Iceberg table metadata, storing the lineage graph in a queryable DynamoDB graph store, and exposing a REST API for lineage traversal. The tracker enables impact analysis (which downstream tables are affected by a source change?) and root cause analysis (where did this column's value originate?).

This TDD builds on the Iceberg table format from [[ADR-0023|ADR-0023: Use Apache Iceberg for Data Lake Format]] and integrates with the lineage data generated by the dbt transformation layer from [[ADR-0022|ADR-0022]].

## Overview

The Data Lineage Tracker is a Python Lambda service that runs post-dbt-run to parse the dbt `manifest.json` artifact and extract node-to-node lineage edges. It stores lineage as a directed acyclic graph in DynamoDB (nodes = table/column identities; edges = upstream/downstream relationships) and exposes a REST API via API Gateway for lineage traversal queries. The tracker supports two query types: upstream traversal (find all sources of a given table) and downstream impact analysis (find all tables affected by a source change).

Key design principles:
- **dbt manifest as source of truth**: Lineage is parsed from dbt's own `manifest.json` rather than SQL parsing; this ensures accuracy for all supported dbt materialization types
- **Column-level granularity**: The graph stores column-level edges where dbt provides them via `column_lineage` in the manifest
- **Immutable snapshots**: Each dbt run creates a new lineage snapshot; historical snapshots are retained for 30 days to support impact analysis at a point in time
- **API-first**: All lineage reads go through the REST API; no direct DynamoDB access by consumers

## Architecture

### Component Diagram

The tracker has three modules:

- **Manifest Parser**: Reads `manifest.json` from S3 post-dbt-run; extracts node definitions, dependencies, and column-level lineage edges
- **Graph Store**: Writes lineage nodes and edges to DynamoDB; manages snapshot versioning and TTL
- **Lineage API**: API Gateway + Lambda REST API; handles upstream/downstream traversal queries using iterative BFS on DynamoDB graph edges

### Graph Data Model

Nodes represent tables or columns. Edges represent upstream (depends_on) relationships.

- Node key format: `{layer}.{schema}.{table}` (e.g., `marts.analytics.orders_daily`)
- Column node key: `{layer}.{schema}.{table}.{column}`
- Edge direction: `upstream` (source → target represents "source is upstream of target")

## Information Model

### Core Entities

- **LineageNode**: DynamoDB item. Fields: `node_id`, `node_type` (table|column), `layer`, `schema`, `table`, `column` (optional), `snapshot_id`, `created_at`
- **LineageEdge**: DynamoDB item. Fields: `edge_id`, `upstream_node_id`, `downstream_node_id`, `snapshot_id`, `edge_type` (table|column), `created_at`
- **LineageSnapshot**: DynamoDB item. Fields: `snapshot_id`, `dbt_run_id`, `node_count`, `edge_count`, `created_at`, TTL set to 30 days

### DynamoDB Tables

- `lineage_nodes` table: partition key `node_id`, sort key `snapshot_id`; GSI on `(layer, schema, table)` for table lookups
- `lineage_edges` table: partition key `upstream_node_id`, sort key `downstream_node_id#snapshot_id`; GSI on `(downstream_node_id, snapshot_id)` for upstream queries
- `lineage_snapshots` table: partition key `snapshot_id`; GSI on `created_at` for latest-snapshot queries

## Interfaces

### REST API

- `GET /lineage/{node_id}/upstream?snapshot_id=latest&depth=3` — Traverse upstream dependencies up to `depth` hops
- `GET /lineage/{node_id}/downstream?snapshot_id=latest&depth=3` — Find all downstream dependents
- `GET /lineage/snapshots` — List available lineage snapshots
- `GET /lineage/{node_id}?snapshot_id={id}` — Get node metadata and direct edges

### Traversal Response Format

```json
{
  "node_id": "marts.analytics.orders_daily",
  "direction": "upstream",
  "depth": 2,
  "nodes": [
    {"node_id": "staging.raw.orders", "depth": 1},
    {"node_id": "staging.raw.customers", "depth": 1},
    {"node_id": "raw.kafka.order_events", "depth": 2}
  ],
  "edges": [...]
}
```

## Work Plan

1. **Phase 1 — Manifest Parser (Week 1-2)**: dbt manifest.json parsing, node/edge extraction, table-level lineage DynamoDB writes
2. **Phase 2 — Traversal API (Week 3)**: BFS upstream and downstream traversal, API Gateway integration, depth-limited queries
3. **Phase 3 — Column-Level Lineage (Week 4)**: Column-level edge extraction from manifest `column_lineage` nodes, column traversal endpoints
4. **Phase 4 — Snapshot Management (Week 5)**: Snapshot versioning, TTL management, historical query support
5. **Phase 5 — Integration (Week 6)**: Airflow post-dbt-run trigger, lineage dashboard integration, accuracy validation against known lineage chains

## Risks and Mitigations

- **Risk**: dbt manifest format changes between dbt versions break the parser. **Mitigation**: Parser is versioned by manifest schema version; CI tests validate parser against manifests from dbt 1.5, 1.6, and 1.7.
- **Risk**: DynamoDB query cost for deep traversals on large graphs. **Mitigation**: Traversal depth is capped at 10 hops; BFS is bounded; API Gateway response timeout is 29 seconds.
- **Risk**: Lineage drift between manifest snapshots causes stale impact analysis. **Mitigation**: Snapshot ID is always included in API responses; consumers are expected to use `snapshot_id=latest` for current state.
- **Risk**: Column-level lineage is incomplete for models using `*` select or dynamic SQL. **Mitigation**: Nodes without column-level edges fall back to table-level lineage only; API response indicates lineage confidence level per node.

## Operations

- **Deployment**: Lambda deployed via Terraform; triggered by Airflow post-dbt-run DAG task.
- **Monitoring**: CloudWatch metrics for parsing latency, node/edge write count per run, traversal query latency.
- **Alerting**: Alert on manifest parsing failure (blocks lineage update), traversal API P95 > 5 seconds.
- **Rollback**: Previous Lambda version redeployed via alias; DynamoDB snapshot data is immutable and versioned by snapshot ID.
