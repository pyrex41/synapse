## Steps

### Step 1: Query Submission

The user types a search query into the search box and presses Enter or clicks the search button. The frontend validates that the query is non-empty (minimum 2 characters), then issues a GET request to the Search Query Processing Service: `GET /v1/search?q={encoded_query}&page=1&limit=20`. The request includes the user's session ID as a cookie and, if logged in, a JWT bearer token.

### Step 2: Query Parsing and Rewriting

The Search Query Processing Service's Lambda function receives the request. The query parser tokenizes and normalizes the raw query string, producing an AST. The rewrite pipeline applies synonym expansion and field boost annotations from the DynamoDB configuration store. If the query contains recognized navigational patterns (e.g., exact product name), the query is classified as navigational and bypasses the standard ranking pipeline.

### Step 3: Parallel Retrieval

The service executes two parallel Elasticsearch queries: a BM25 `multi_match` query across `title`, `description`, and `tags` fields, and (if hybrid search is enabled) a `knn` vector query using the query embedding generated inline. The query embedding is generated by calling the OpenAI embedding API with a 50ms timeout; if the embedding times out, only the BM25 query is used. Both queries are executed against the `search-content-read` alias.

### Step 4: Re-ranking and Fusion

BM25 results and ANN results (if available) are merged using Reciprocal Rank Fusion with `k=60`. The merged top-100 candidates are sent to the Search Relevance Engine for LightGBM re-ranking, with a 30ms timeout. If the Relevance Engine times out or is unavailable, the RRF-merged order is used directly. The top 20 results from the final ranking are selected for the response.

### Step 5: Response Serialization

The service serializes the top 20 results with field masking (only title, excerpt, URL, content type, and publish date are returned), adds pagination metadata (total count, current page, next page URL), and returns the response to the frontend. A `search-query-id` UUID is generated and included in the response headers for analytics correlation.

## Expected Results

- User sees a result list within 200ms P95 of submitting the query
- Results are ranked by relevance with the most relevant document at position 1
- If hybrid search is enabled, semantically similar results appear even without exact keyword matches
- If the query returns zero results, an empty list is returned with suggestions for alternative queries
- The search-query-id from the response is used to correlate future click events to this search session
