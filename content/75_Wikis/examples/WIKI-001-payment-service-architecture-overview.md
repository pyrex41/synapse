## Overview

The Payment Service is a Go microservice that provides the core payment processing capabilities for the platform. It handles authorization, capture, refund, and void operations through a hexagonal architecture with pluggable gateway adapters for Stripe and PayPal.

This page was auto-generated by analyzing the repository source files. It covers the structural architecture of the `payment-service` codebase. For operational runbook details see RUNBOOK-071.

## Architecture

The service is structured in four concentric layers following the hexagonal (ports and adapters) pattern:

- **Handler Layer** (`internal/handler/`): HTTP request validation, JWT claim extraction, rate limiting enforcement. Routes requests to use cases.
- **Use Case Layer** (`internal/usecase/`): Core business logic. Enforces idempotency, runs state machine transitions, orchestrates gateway calls, publishes events to SQS.
- **Gateway Adapter Layer** (`internal/gateway/`): Implements the `PaymentGateway` interface for Stripe and PayPal. Wrapped in circuit breaker middleware (5 failures in 30s → open state, 60s recovery window).
- **Repository Layer** (`internal/repository/`): PostgreSQL persistence using `pgx` v5. Uses `SELECT FOR UPDATE` on payment rows during state transitions to prevent race conditions.

## Key Components

- **`PaymentGateway` interface** - The central abstraction. All gateway-specific code lives behind this interface, making it trivial to add new providers.
- **`PaymentUseCase`** - Orchestrates the full payment lifecycle. Checks idempotency cache before any mutation, validates state machine transitions, wraps DB writes and event publishing in a single transaction.
- **`Money` value object** - Carries amount + currency together. Arithmetic methods enforce currency matching and prevent silent precision errors.
- **`PaymentEvent` table** - Append-only audit log. Every state change produces an immutable event row with previous state, new state, gateway response, and actor.
