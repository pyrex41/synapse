## Overview

The `grafana-provisioning` repository manages the automated configuration of all Grafana instances in the monitoring stack. Rather than manually configuring Grafana through its UI (where changes are ephemeral and undocumented), all configuration — data sources, dashboards, alert contact points, and notification policies — is expressed as code and applied by a provisioning pipeline.

This page documents the provisioning architecture, the conventions for adding new dashboards and data sources, and the automation that keeps Grafana configuration in sync with changes in the codebase.

This wiki was generated by analyzing the provisioning repository structure and configuration files. For operational information about the Grafana instances themselves, see the Grafana Dashboard Templates wiki (WIKI-031) and the Monitoring Stack Architecture Overview (WIKI-029).

## Key Components

### Provisioning Directory Structure

Grafana loads provisioning configuration from `/etc/grafana/provisioning/` at startup and watches for changes (hot-reload is enabled). The repository maps directly to this directory structure:

```
grafana-provisioning/
├── datasources/
│   ├── prometheus.yaml         # Prometheus remote-read datasource
│   ├── prometheus-local.yaml   # Local Prometheus for alerting rules
│   ├── jaeger.yaml             # Distributed tracing datasource
│   ├── loki.yaml               # Log aggregation datasource
│   └── alertmanager.yaml       # AlertManager datasource
├── dashboards/
│   ├── dashboards.yaml         # Dashboard provider configuration
│   ├── platform/               # Monitoring platform dashboards
│   ├── services/               # Per-service dashboards (auto-generated)
│   ├── slo/                    # SLO dashboards
│   └── oncall/                 # On-call overview dashboards
├── alerting/
│   ├── contact-points.yaml     # Notification channels (Slack, PagerDuty)
│   ├── notification-policies.yaml  # Routing tree
│   └── mute-timings.yaml       # Maintenance window mute configurations
├── plugins/
│   └── plugins.yaml            # Pre-installed plugin declarations
└── scripts/
    ├── generate-service-dashboards.sh  # Dashboard templating script
    └── validate.sh             # Pre-commit validation script
```

### Dashboard Provider Configuration

`dashboards/dashboards.yaml` configures Grafana to watch the provisioning directories for dashboard JSON files. Key settings:

```yaml
apiVersion: 1
providers:
  - name: Platform Dashboards
    type: file
    disableDeletion: true      # Prevents deletion via UI
    updateIntervalSeconds: 60  # Hot-reload interval
    allowUiUpdates: false      # Prevents manual edits being persisted
    options:
      path: /etc/grafana/provisioning/dashboards/platform
      foldersFromFilesStructure: true
```

`allowUiUpdates: false` is intentional. Engineers who edit dashboards in the Grafana UI will see their changes reset on the next reload. All dashboard changes must go through the provisioning repository. This is documented in the new engineer onboarding docs.

### Data Source Configuration

Each data source is a separate YAML file. The Prometheus data source configuration specifies the remote-read endpoint, scrape interval alignment, and exemplar support:

```yaml
apiVersion: 1
datasources:
  - name: Prometheus
    type: prometheus
    url: http://prometheus.monitoring.svc:9090
    access: proxy
    isDefault: true
    jsonData:
      timeInterval: "15s"
      queryTimeout: "60s"
      httpMethod: POST
      exemplarTraceIdDestinations:
        - name: traceID
          datasourceUid: jaeger
```

The `exemplarTraceIdDestinations` configuration links Prometheus exemplars to the Jaeger datasource, enabling click-through from metrics to traces in dashboards.

## Architecture

### Provisioning Pipeline

Configuration changes follow this flow:

1. Engineer opens a PR in `grafana-provisioning` with dashboard JSON or YAML changes
2. CI runs `scripts/validate.sh` which: validates JSON schema for all dashboard files, checks YAML syntax for provisioning configs, verifies all referenced datasource UIDs exist, and lints for common mistakes (hardcoded time ranges, missing variables)
3. PR is reviewed and merged to `main`
4. A Kubernetes ConfigMap is updated via GitOps (ArgoCD watches the repository)
5. The ConfigMap volume mounts are updated in the Grafana deployment; Grafana hot-reloads the changed files within 60 seconds

Grafana restarts are not required for dashboard and data source changes. They are only required for plugin changes, which require the plugins to be present in the container image.

### Service Dashboard Generation

The most frequently added content is per-service dashboards. Rather than requiring teams to write dashboard JSON from scratch, the provisioning repository includes a templating script that generates a standard service dashboard from a simple YAML descriptor:

```yaml
# services/alert-management.yaml
service: alert-management
job_label: alert-management
datasource: Prometheus
panels:
  - type: request_rate
  - type: error_rate
  - type: latency_p50_p95_p99
  - type: active_alerts_count
  - type: routing_rules_count
```

Running `scripts/generate-service-dashboards.sh` processes all YAML descriptors in `dashboards/services/` and produces Grafana-compatible dashboard JSON files. The generated JSON is committed to the repository and tracked in version control.

Teams add new service dashboards by adding a YAML descriptor and running the generator locally. The CI pipeline validates the generated JSON before merging.

## Configuration

### Alerting Configuration

Grafana's built-in alerting is not used. All alerting is managed by Prometheus alert rules and AlertManager. The `alerting/contact-points.yaml` file configures the contact points that AlertManager routes to (Slack and PagerDuty), but these are referenced by AlertManager, not evaluated by Grafana.

The AlertManager datasource is configured to allow Grafana to display current firing alerts and silences in dashboards, but Grafana does not evaluate alert rules.

### Secrets Management

Data source credentials (API keys, tokens) are not stored in the provisioning repository. Instead, the provisioning YAML files reference Kubernetes Secret names, which Grafana resolves at runtime:

```yaml
jsonData:
  httpHeaderName1: "Authorization"
secureJsonData:
  httpHeaderValue1: "$__env{GRAFANA_LOKI_API_KEY}"
```

Secrets are managed separately and injected via the Grafana deployment's environment variables. Rotating a credential requires updating the Kubernetes Secret; no provisioning repository change is needed.

## Dependencies

| Component | Role |
|-----------|------|
| ArgoCD | GitOps operator; syncs ConfigMaps from the provisioning repository to the cluster |
| Kubernetes ConfigMaps | Intermediate storage for provisioning files between the repository and Grafana pods |
| Prometheus | Primary metrics data source |
| Jaeger | Distributed traces data source; linked via exemplar configuration |
| Loki | Log aggregation data source |
| AlertManager | Alert routing state datasource (display only) |
